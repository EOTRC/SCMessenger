## 5. Coverage gaps (what is missing from this capture)

1. **Zero app-level (`MeshRepository`/`BleGatt*`/`MeshEventBus`/`SwarmBridge`/`mesh_ble_*`) log lines exist anywhere before `14:01:32.416`** in any of the three files, despite the scmessenger app being in the foreground and (per PSS/lifecycle evidence) running continuously from `13:40:37.854` (pid 15783) through `13:43:28.566`, and again from `13:43:41.141` (pid 16775) onward. This means the entire first app session (pid 15783, ~2m50s) and the first ~18 minutes of the second app session (pid 16775, `13:43:41`-`14:01:25`) have no app-level log coverage at all -- this is exactly the interval in which the operator reports "Hiccup 1" (Android stopped receiving messages) occurred.
2. **The operator's stated test-window start of `13:35` has no corresponding app activity.** The first scmessenger process start in any file is `13:40:37.854`; nothing tagged to the app (process, activity, or mesh) appears between `13:35:00` and `13:40:37` in the ~25.6k-line window capture.
3. **`FileLoggingTree: Truncating log file: /data/user/0/com.scmessenger.android/files/mesh_diagnostics.log`** at `14:01:57.521` (single occurrence, `window_1300_1402_filtered.log:25225`) indicates the app maintains its own on-device diagnostics log file that is truncated during the capture window; its pre-truncation contents (which could cover the gap in item 1) are not part of any of the three supplied files.
4. **No BLE/GATT stack-level logging** (e.g. Android Bluetooth HCI/GATT internal tags, `btsnoop`, `BluetoothGatt` framework-level connection-state codes) is present anywhere in the window capture -- only the app's own `BleGattServer`/`BleGattClient` wrapper log lines are visible. The brief notes the window capture has "the noisiest system tags stripped," and Bluetooth stack internals may be among what was stripped.
5. **Hiccup 2 (operator turned Bluetooth off, messaging still worked) has no corresponding log evidence** in any of the three files. No `BluetoothAdapter` STATE_OFF/STATE_TURNING_OFF transition, and no `isLeEnabled(): OFF`, appears anywhere in the window capture, which ends at `14:02:29.240` -- either this event happened after the capture ended, or it is not tagged in a way this filtered capture retained.
6. **The macOS CLI and Windows CLI nodes are never referenced by any identifier** (peer id, IP, nickname) in any of the three files. Only one remote peer (`12D3KooWJUJ1koSWwSEAX32z6SGaepikyqpJawpojoy6gvQ8k688` / `ChristyLove`) and one non-self IP (`192.168.0.142`) appear anywhere in the capture (see Section 3, items 1-2). There is no log evidence either confirming or ruling out that those CLI nodes were reachable on the LAN during the test window.
7. **No iOS-side log data** is present in any of the three files (all three are Android logcat captures); the "succeeded overall" cross-platform exchange can only be partially reconstructed from the Android side.
8. **`window_1300_1402_filtered.log` is described as having "the noisiest system tags stripped"** -- the exact list of stripped tags is not stated in the brief or discoverable from the file itself, so it is not possible to know from this capture alone whether relevant tags (e.g., raw Bluetooth/Wi-Fi driver tags) were among those removed.
9. **Message content is never present** in any delivery_attempt/receipt log line (only ids, byte counts, and sha256-64 payload hashes), so it is not possible to correlate specific log lines to specific human-readable messages the operator sent/received during the test.
